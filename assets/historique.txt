# Historique du projet - Mise à l'échelle (MongoDB sharded)

## Approche initiale
- Étudier l'architecture d'un cluster MongoDB sharded : routeurs (mongos), serveurs de configuration (config servers, replica set), shards (chaque shard est un replica set).
- Définir l'ordre de démarrage logique : config servers -> shards -> routeurs -> initialisation (rs.initiate, addShard, enableSharding/shardCollection) -> import de données.
- Mettre en place un `docker-compose.yml` avec noms imposés, réseau commun, volumes persistants et ports exposés pour les routeurs.

## Difficultés rencontrées et solutions
1. **Méconnaissance partielle de Docker/Compose**
   - Difficulté : projection difficile sur la création de nombreux conteneurs interdépendants et sur la persistance.
   - Solution : étude de la documentation Docker/Compose et des exemples MongoDB sharded; utilisation de volumes nommés, réseau dédié, `depends_on`, et d'un conteneur d'initialisation.

2. **Peu d'expérience NoSQL/MongoDB en projet réel**
   - Difficulté : comprendre les rôles (configsvr, shardsvr, mongos), la réplication et le sharding.
   - Solution : schéma d'architecture (assets/cluster_mongo_schema.png) et tests progressifs (ping, rs.status, sh.status, distribution des chunks).

3. **Ordre d'initialisation et disponibilité des services**
   - Difficulté : `rs.initiate`, `addShard` et `shardCollection` échouent si les membres ne sont pas prêts.
   - Solution : script Python d'init avec réessais/attente (`init_cluster.py`) et exécution dans un conteneur `init_cluster` après démarrage des dépendances.

4. **Cohérence ports/rôles MongoDB**
   - Difficulté : config servers en 27019, shards en 27018 (shardsvr), mongos en 27017; erreurs de connexion si ports mélangés dans les URI de replica set.
   - Solution : ports explicites par rôle et configuration des membres de replica set avec le bon port (`host:27018` pour shards, `host:27019` pour config).

5. **Import et format des données "books"**
   - Difficulté : s'assurer que la collection est shardée et alimentée pour les tests d'éclatement.
   - Solution : activation du sharding sur la base `books`, `shardCollection` sur `_id` hashed, import automatique depuis `scripts/books.txt` (JSON étendu) au démarrage.

6. **Historique des modifications**
   - Difficulté : conserver une trace des changements sans interface shell complexe.
   - Solution : service `historique` qui s'abonne aux change streams du cluster via pymongo et journalise les opérations dans un volume persistant.
